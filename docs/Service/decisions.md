# decisions.md — Журнал архитектурных решений (Architecture Decision Records)

## ADR-001: Реализация инвертированного индекса и BM25 с нуля
- **Статус:** Принято (Обязательное академическое требование).
- **Контекст:** Требования курса НИРС на кафедре ИУ5 запрещают использование готовых библиотек ранжирования (Elasticsearch, Lucene, rank-bm25).
- **Решение:** Инвертированный индекс строится с нуля с использованием SPIMI-пайплайна. Ранжирование вычисляется по формуле $IDF(t) = \ln(1 + \frac{N - DF(t) + 0.5}{DF(t) + 0.5})$ с параметрами $k_1 = 1.5, b = 0.75$.
- **Последствия:** Полная прозрачность вычислений, возможность тонкой оптимизации токенизации под стектрейсы, соблюдение правил кафедры.

## ADR-002: Межсервисный протокол на базе gRPC
- **Статус:** Принято.
- **Контекст:** Требуется высокоскоростное сетевое взаимодействие между шлюзом `gateway` и поисковым ядром `search_engine_core` с минимальными накладными расходами на сериализацию.
- **Решение:** Использовать протокол gRPC (HTTP/2) со строго типизированными Protobuf-контрактами (`protos/search.proto`, `protos/graph.proto`).
- **Последствия:** Строгий контракт API, автоматическая кодогенерация клиентов, минимальные сетевые задержки при передаче больших списков релевантных тредов.

## ADR-003: Интерактивный граф связей тредов в результатах поиска
- **Статус:** Принято.
- **Контекст:** Разработчикам требуется возможность исследовать смежные ошибки и решения (например, дубликаты вопросов или темы, на которые ссылаются авторы ответов).
- **Решение:**
  - В ядре поиска накапливается граф связей между самими тредами (вопросами на Stack Overflow), а не абстрактных сущностей.
  - Для хранения связей используется встраиваемая база данных SQLite (`data/index/graph.db`) с индексами по `source_doc_id` и `target_doc_id`. Это обеспечивает быстродействие выборки подграфа ($< 1$ мс) и упрощает протокол взаимодействия между Индексатором и Ядром.
  - В веб-интерфейсе реализуется интерактивный граф связей, встроенный прямо в страницу результатов поиска (`/search`).
- **Последствия:** Уникальное конкурентное преимущество, наглядная визуализация контекста без необходимости строить сложные онтологические связи, надежное хранение без ручного кодирования смещений.

## ADR-004: Аутентификация, SSO и разделение прав (RBAC)
- **Статус:** Принято.
- **Контекст:** Необходим удобный вход для разработчиков без запоминания паролей, защита LLM квот, выпуск персональных API-ключей для MCP и закрытый доступ к панели администратора.
- **Решение:**
  - Реализовать SSO через OAuth2 и OpenID Connect (GitHub, Google, корпоративный IdP).
  - Выпускать пару JWT токенов (Access + Refresh).
  - Реализовать RBAC с ролями `guest`, `developer`, `admin`.
  - Предоставить администраторам доступ к `/admin` для контроля состояния индекса и промптов RAG.
- **Последствия:** Безопасность корпоративного уровня, контроль расхода токенов LLM, гибкость интеграций.

## ADR-005: Интеграция с кодинг-ассистентами через Remote MCP
- **Статус:** Принято.
- **Контекст:** Разработчики пишут код в современных IDE (Cursor, Claude Code, Windsurf) и нуждаются в получении проверенных решений Stack Overflow непосредственно в контекст чата IDE.

## ADR-006: Star Map — карта связей тредов на Vanilla Canvas с собственной force-симуляцией
- **Статус:** Принято.
- **Контекст:** FR-3 требует интерактивный граф связанных SO-тредов. Фронтенд проекта — строго Vanilla JS/HTML5/CSS3 без фреймворков и внешних библиотек. Точка входа — кнопка в карточке RAG-ответа с анимированным уходом чата и prompt bar (FR-3.4). До готовности `GraphService` данные мокируются (FR-3.5).
- **Решение:**
  - Отрисовка на HTML5 Canvas 2D; force-симуляция (отталкивание, пружины ребер, центрирование, затухание) реализуется вручную — без D3.js, Cytoscape, React Flow и иных готовых библиотек визуализации.
  - Цвета категорий узлов по FR-3.2 (`#10b981`, `#f59e0b`, `#38bdf8`, `#a855f7`), радиус $\propto \sqrt{Score}$; интерактив hover/click по FR-3.3 (стеклянный тултип и панель деталей в дизайн-системе Errorium).
  - Мок-билдер графа строит узлы из источников RAG-ответа (`PRIMARY_RESULT` / `OTHER_RESULT`) и пула связанных тредов (`DUPLICATE` / `LINKED`); структура полей повторяет `ThreadNode` / `ThreadEdge` из `protos/graph.proto`.
  - Переходы — CSS-анимации (fade + scale + blur) чата и prompt bar; маршрут `/star-map` через History API, возврат по `Esc` / `Back to chat`.
- **Последствия:** Нулевые внешние зависимости, полный контроль производительности и визуальной консистентности с дизайн-системой; переход на реальный `GetThreadGraph` / `GetThreadDetails` ограничивается заменой источника данных без переписывания слоя визуализации.

## ADR-007: Потоковое чтение дампа и хеш-выборка корпуса вместо распаковки и префикса
- **Статус:** Принято (2026-11-18), реализуется Ролью 1.
- **Контекст:** Архив `stackoverflow.com.7z` весит 64 ГиБ, `Posts.xml` распакованный — 105.6 ГБ (весь архив ≈ 360 ГБ). Замеры показали, что архив несолидный (файл извлекается отдельно), а `Posts.xml` не отсортирован по `Id`: ответы лежат вдали от вопросов, и на префиксе 3 ГиБ найден лишь 12% принятых ответов.
- **Рассмотрено:**
  1. Полная распаковка на диск — нецелесообразна (≈ 360 ГБ при том, что нужны три файла из десяти).
  2. Префикс «первые N ГБ» — даёт вопросы без ответов и смещение в ранние годы; отклонено.
  3. Потоковое чтение (`7zz x -so`) + детерминированная выборка по хешу `Id` треда (ответ выбирается по хешу `ParentId`) + расширение корпуса соседями из `PostLinks.xml` — принято.
- **Решение:** см. `docs/Tech/03-data.md`, раздел 4. Режим `sample` для КТ2 (≈ 1% тредов, воспроизводимо), режим `full` для КТ3 — повтор того же прохода по `K` хеш-шардам со слиянием блоков SPIMI.
- **Последствия:** Диск не зависит от размера дампа; выборка равномерна по годам и тегам; результат воспроизводим (манифест выборки). Цена — полный проход `Posts.xml` (≈ 10 мин) на каждую выборку и необходимость расширения соседями, иначе граф тредов вырождается.

## ADR-008: Python и стандартная библиотека для индексатора
- **Статус:** Принято (2026-11-18), Роль 1.
- **Контекст:** Dockerfile индексатора был пуст, язык не фиксировался. Тесты проекта (`tests/unit`, `make test-unit`) и поисковое ядро (`make proto` через `grpc_tools`) ориентированы на Python; бинарный формат индекса (`03-data.md`, п. 1) от языка не зависит.
- **Решение:** индексатор и токенизатор пишутся на Python 3 с использованием только стандартной библиотеки (`re`, `struct`, `sqlite3`, `subprocess`, `heapq`, `multiprocessing`); готовые поисковые и ранжирующие библиотеки запрещены (ADR-001). Потоковое чтение XML — построчное, регулярными выражениями по строке `<row .../>`, без загрузки файла в память; архив читается подпроцессом `7zz x -so`.
- **Последствия:** единый язык с ядром и тестами, токенизатор можно подключить в ядро без дублирования. Минус — скорость на полном дампе: разбор и токенизация 100 ГБ на Python дорогие, поэтому режим `full` построен на хеш-шардах, которые параллелятся по ядрам (`multiprocessing`); для `sample` (≈ 1 ГБ текста) скорость достаточна. Горячие места при необходимости оптимизируются без смены формата индекса.

## ADR-009: Индексатор запускается отдельным compose-файлом по требованию
- **Статус:** Принято (2026-11-18), Роль 1.
- **Контекст:** Индексатор — офлайн-задача (минуты–часы), а не долгоживущий сервис. Основной `docker-compose.yml` используется автодеплоем (`.github/workflows/deploy.yml`) и содержит только работающие сервисы; сервисы ядра и индексатора из него были временно убраны.
- **Решение:** Отдельный `docker-compose.indexer.yml` и цели `make index-sample` / `make index-corpus`. Архив дампа монтируется только на чтение (`SO_DUMP_DIR`), лимит памяти контейнера 4 ГБ соответствует бюджету индексатора, подкоманда CLI (`sample`, `corpus`) выбирает режим.
- **Последствия:** автодеплой и dev-стек не затрагиваются; все команды по-прежнему выполняются в контейнере через Make (`AGENTS.md`, п. 5). Цена — ещё один compose-файл; при появлении сервиса ядра в основном compose индекс читается из общего тома `data/index` (read-only).

## ADR-010: REST-контракт Gateway v1 — «Ядро + стабы», источник истины openapi.yaml
- **Статус:** Принято (2026-11-19), Роль 3.
- **Контекст:** Фронтенд полностью на моках (ни одного `fetch`), хендлеры gateway написаны, но не подключены (регистрируется только `/health`); обнаружены баги: два разных типа context key у middleware и handler (чаты всегда 401), отсутствие проверки владельца чата, возможность самоназначения роли `admin` через `PATCH /users/me`. Схема БД не покрывает UI: нет полей профиля (gender, language, профессиональная «роль») и текста/кода RAG-ответа. Поисковое ядро (Роль 2) ещё не реализовано.
- **Решение:**
  1. Источник истины REST-контракта — `services/gateway/api/openapi.yaml` (OpenAPI 3.0.3), составленный по фактическому поведению фронтенда; gateway отдаёт его на `/openapi.yaml` и Swagger UI на `/docs` (go:embed). Операции помечены `x-status: core|planned`.
  2. Итерация «Ядро + стабы»: wiring всех хендлеров, auth на bcrypt (`golang.org/x/crypto`, допущен владельцем), профиль + аватар через Garage S3 (`aws-sdk-go-v2`), чаты с проверкой владельца, search/graph/tags/status — детерминированные стабы за интерфейсами `SearchClient`/`GraphClient` (замена на gRPC без изменения REST-контракта). SSO, сброс пароля, MCP-токены, SSE, admin — только контракт (`planned`).
  3. `role` (RBAC `user|admin`) отделён от `profession` («роль» в UI); `role` недоступен для изменения клиентом. Миграция `000002`: `users.profession/gender/language`, `chat_messages.content/code`.
  4. Аватар: без конвертации в WebP, приватный бакет, ключ `avatars/{user_id}`, публичная выдача прокси-роутом `GET /api/v1/users/{id}/avatar` (`<img>` не умеет Bearer); `avatar_url` — относительный прокси-путь.
  5. Ошибки — единый `{"error": msg}`; чужие ресурсы → 404; два score у источника (`question_score` — голоса SO, `bm25_score` — релевантность); теги `[Python]` извлекаются из текста запроса и нормализуются в lowercase.
- **Последствия:** фронтенд получает стабильный контракт для замены моков; стабы изолируют незрелость ядра; пакет задач для внешней команды исполнителей (`handoff/gateway-backend/`) опирается только на этот контракт. Цена — расхождение с прежним текстом docs (WebP-аватар, «role» в UI) устранено правкой `03-data.md`/`04-api-and-access.md`; политика MCP-токенов остаётся нерешённой (FR-4.4 vs §3.4) и требует решения владельца до реализации `planned`-части.

## ADR-011: Итерация 2 «Финал до КТ3» — ядро, MCP-гибрид, LLM OpenAI/GigaChat, три волны
- **Статус:** Принято (2026-11-19), владелец продукта. Итерация 1 (T1–T8) выполнена и влита (мердж `e134fa4`), гейты зелёные.
- **Контекст:** до КТ3 остаются: пустой `search_engine_core` (Роль 2), отсутствие `benchmark/evaluate.py`, устаревший `make proto` (Python-кодоген в Go-gateway), planned-часть gateway (SSO, пароли, MCP, SSE, admin), фронтенд на моках. Противоречие MCP-политики (FR-4.4 vs 03-data §3.4) не решено. Учебный проект: нужен бесплатный LLM-вариант.
- **Решение:**
  1. **Три линейные волны** в пакете `handoff/gateway-final/`: A — поисковое ядро (Python, переиспользует токенизатор и читатели формата индексатора, ADR-008/§5.6) + benchmark + кодоген/compose; B — gateway planned-часть (gRPC-адаптеры вместо стабов, LLM+SSE, SSO, пароли, MCP, admin); C — интеграция фронтенда (замена моков на fetch, Vanilla JS без фреймворков).
  2. **MCP — ГИБРИД** (решение владельца): `/sse` + `/mcp/messages` работают без токена (анонимно); с Bearer `err_live_…` — привязка к пользователю и аудит. Таблица `mcp_tokens` добавляется миграцией `000003` (один токен на пользователя, SHA-256 хэш). Противоречие FR-4.4/§3.4 снято. **→ Заменено ADR-012 до реализации: токены убраны полностью.**
  3. **LLM — два провайдера + стаб** (`rag_config.provider`: `openai | gigachat | stub`): OpenAI-совместимый клиент с настраиваемым `base_url` (OpenAI/прокси/vLLM/Ollama) и GigaChat (OAuth client_credentials `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, scope `GIGACHAT_API_PERS` — бесплатный для физлиц, токен 30 мин; API `https://api.giga.chat/v1` — новый адрес для подключений после 17.07.2026, старый `gigachat.devices.sberbank.ru` выводится; TLS — корневой сертификат НУЦ Минцифры, путь через env). При недоступности LLM — деградация до шаблонного синтеза, поиск не ломается (NFR).
  4. **SSE-формат** единый: `delta {"text":…}` → `done {полный JSON}` → `error {"error":…}`; для сообщений чата первым `user_message`. Заголовок `X-Accel-Buffering: no` против буферизации nginx.
  5. **`ReloadIndex`** добавлен в `protos/search.proto` (горячая перезагрузка индекса для Admin API); кодоген: Go-плагины для gateway, `grpc_tools` для ядра; `make proto` чинится.
  6. **SSO и почта:** полный код OAuth2-флоу (GitHub/Google/Yandex, stdlib, state в БД) и сброса пароля (SMTP через env; без SMTP — dev-отправитель пишет ссылку в лог). Реальные ключи/SMTP владелец подставляет позже; тесты на моках IdP/SMTP.
- **Последствия:** все операции openapi.yaml становятся `core`; ядро и gateway связываются только по gRPC; фронтенд получает реальные данные без изменения контракта. Цена — пакет большой (18 задач), для слабой команды строго линейное исполнение с гейтами после каждой задачи; GigaChat требует сертификата НУЦ Минцифры в окружении (инструкция в пакете).

## ADR-012: MCP без токенов — открытый доступ с лимитами (заменяет п.2 ADR-011)
- **Статус:** Принято (2026-11-19), владелец продукта. Действует до реализации волны B.
- **Контекст:** в гибридной схеме (ADR-011 п.2) токен ничего не запирает — анонимный доступ разрешён, токен даёт лишь атрибутцию. Цена: таблица `mcp_tokens`, AES-GCM-хранение для показа в модалке, 2 REST-эндпоинта, отдельная middleware, усложнение B5/C4 для слабой команды. При этом per-IP лимиты запросов опасны для защиты: весь зал за NAT бауманского WiFi придёт с одного IP и будет заблокирован.
- **Решение:**
  1. Персональные MCP-токены **убраны полностью**: нет таблицы `mcp_tokens`, нет `/api/v1/mcp/token*`, нет `tokenutil`. `/sse` и `/mcp/messages` — открытый доступ. FR-4.4 переписан, модалка MCP и лендинг показывают URL + JSON-конфиг без заголовков авторизации (конфиг фронтенд строит сам из `location.origin`).
  2. Защита от абьюза — лимиты, не блокирующие общий IP:
     - ≤ `MCP_MAX_SESSIONS_PER_IP` (100) **одновременных SSE-сессий** с IP (X-Real-IP от nginx, fallback RemoteAddr) → 429 + Retry-After;
     - ≤ `MCP_MAX_SESSIONS` (200) сессий глобально → 503 + Retry-After;
     - ≤ `MCP_CALLS_PER_MIN` (60) `tools/call` в минуту **на сессию** → 429;
     - ≤ `LLM_MAX_CONCURRENT` (8) одновременных LLM-вызовов глобально (RAG, чаты, MCP) → ожидание до 2 с, затем деградация до шаблонного синтеза (поиск не ломается).
     Все счётчики — in-memory, без схемы БД.
- **Последствия:** миграция 000003 худеет до трёх таблиц; B5/C4 упрощаются; зал на защите с одного IP открывает по сессии на человека и не блокируется; абьюзер ограничен потолками сессий и вызовов. Цена — нет атрибутции вызовов к пользователю и нет задела под персональные лимиты (при необходимости — будущий ADR); публичный `/sse` может расходоваться третьими лицами в пределах лимитов (бесплатный тариф GigaChat защищён деградацией).

## ADR-013: Автодеплой — все прод-образы собираются в CI, сертификат НУЦ в репозитории
- **Статус:** Принято (2026-11-20), инфраструктура. Уточняет ADR-009: ядро вернулось в основной compose как готовый образ.
- **Контекст:** после реализации ядра `search_engine_core` вернулся в `docker-compose.yml` только с `build:` (без `image:`), тогда как CI собирал лишь gateway и frontend, а на сервер доставляются только `docker-compose.yml` и `deploy/`. `docker compose up -d` на сервере пытался собрать ядро из исходников и падал: `resolve : lstat .../Errorium/services: no such file or directory`. Сертификат НУЦ для GigaChat в `deploy/certs/` отсутствовал (каталог сам создал Docker от root), а URL скачивания в docs устарел и отдавал 404.
- **Решение:**
  1. Каждый сервис прод-compose имеет `image:` из GHCR (`ghcr.io/soskiiit/errorium-<name>:develop`); `build:` остаётся для локальной сборки. На сервере ничего не собирается.
  2. CI-матрица собирает три образа: gateway, search-engine-core (context — корень репозитория, Dockerfile `services/search_engine_core/Dockerfile`), frontend. Вход `file` — путь от корня репозитория: buildx резолвит его относительно рабочей директории, не context (проверено экспериментом).
  3. Публичный корневой сертификат НУЦ Минцифры закоммичен в `deploy/certs/russian_trusted_root_ca.crt` (PEM, действует до 27.02.2032) и доставляется scp вместе с `deploy/`. Актуальный URL: `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt` (прежний `content/Other/doc/...` отдаёт 404). Путь `/app/certs/russian_trusted_root_ca.crt` — дефолт `GIGACHAT_CA_CERT` в `pkg/config` gateway (файл гарантированно монтируется compose), переменную можно не задавать.
  4. Prepare-шаг деплоя убирает пустой root-каталог `deploy/certs` (артефакт Docker, иначе scp не запишет сертификат) и создаёт `data/index`, `data/index-benchmark`, `benchmark` от пользователя деплоя.
  5. Регрессия закрыта статическим контрактом `tests/unit/test_deploy_contract.py`: image у всех сервисов, покрытие CI-матрицей build-сервисов, тег `:develop`, состав scp, наличие и валидность PEM-сертификата.
- **Последствия:** деплой не зависит от исходников на сервере; сертификат доедет автоматически. Остаток на стороне окружения (не кода): серверный `.env` деплой не доставляет (нужны `GIGACHAT_*`, `SSO_REDIRECT_BASE`, `FRONTEND_URL` и пр.), индекс нужно положить в `~/Errorium/data/index/` (без него core unready, поиск недоступен).
