# 05-verification.md — Методология тестирования и верификации

## 1. Пирамида тестирования

В соответствии с SDD-методологией проекта, верификация включает 4 уровня:

1. **Unit-тесты (`tests/unit/`):**
   - Модули токенизации (`test_tokenizer.py`): проверка сохранения составных токенов (`NullPointerException`, `C++`, `fmt.Println`).
   - Расчет формулы BM25 (`test_bm25_formula.py`): сверка вычислений $IDF(t)$ и $BM25(q, d)$ с ручным эталонным расчетом кафедры ИУ5.
   - Извлечение графа (`test_thread_graph.py`): валидация корректности построения графа связей между тредами (дубликаты, связанные ответы).
   - JWT & SSO (`test_auth.py`): генерация, валидация сигнатуры, проверка истечения срока действия токена, контроль RBAC.

2. **Интеграционные тесты (`tests/integration/`):**
   - Межсервисный gRPC-канал (`test_grpc_search.py`): корректность сериализации запросов/ответов `SearchService` и `GraphService`.
   - REST API Gateway (`test_api_endpoints.py`): сквозной вызов поиска, RAG-генерации с моком LLM, эндпоинтов админки.
   - MCP Protocol (`test_mcp_sse.py`): вызов инструментов MCP агента через SSE транспорт.

3. **Бенчмаркинг ранжирования (`benchmark/evaluate.py`):**
   - Прогон золотого датасета поисковых запросов и расчет метрик:
     - $Recall@k = \frac{|\text{Релевантные в Top-}k|}{|\text{Все релевантные}|}$ для $k \in \{3, 5, 10\}$
     - $MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$

4. **Нагрузочные тесты и профилирование памяти:**
   - Проверка непревышения 4 ГБ RAM при потоковой индексации.
   - Замер латентности $P_{95} \le 150$ мс при одновременных gRPC-запросах.

---

## 2. Команды для запуска проверок

```bash
# Запуск модульных тестов
make test-unit

# Запуск интеграционных тестов
make test-integration

# Полный тестовый прогон
make test

# Расчет метрик качества поиска (Recall@k, MRR)
make benchmark
```

## 3. Золотой набор benchmark (`benchmark/`)

Набор фиксируется в репозитории **до** сравнения версий поиска и не подгоняется под результаты: одинаковые корпус, вопросы и глубина `k` для каждой версии (занятие 3).

### 3.1. Состав и файлы

| Файл | Содержимое |
| :--- | :--- |
| `benchmark/corpus/documents.jsonl` | 30 документов `D01`–`D30` (JSON Lines, формат режима `corpus` индексатора, `docs/Tech/03-data.md`, п. 4.9) |
| `benchmark/questions.json` | 15 вопросов: 10 обычных (`Q01`–`Q10`) и 5 вопросов-ловушек (`Q11`–`Q15`) с разметкой и эталонами |
| `benchmark/corpus/README.md` | Происхождение документов, лицензия, способ выбора |

**Документ** — тред Stack Overflow (заголовок + вопрос + принятый ответ), очищенный от HTML, с сохранением переводов строк в блоках кода. Поля строки `documents.jsonl`: `doc_id` (1–30; метка `D{doc_id:02d}`), `title`, `text` (`Question: …` и `Answer: …`), `tags`, `so_id`, `url` (ссылка на оригинал для атрибуции).

**Вопрос** (`questions.json`): `id`, `type` (`answerable` или `trap`), `question`, `relevant_docs` (метки `D..`), `reference_answer`.

### 3.2. Правила набора

- Корпус из 30 документов образуют 10 тем по 3 документа; документы выбирались из выборки Stack Overflow режима `sample` (реальные принятые ответы), темы — разные языки и инструменты (Python, Java, C++, C#, Docker, Git, MySQL, CORS).
- Каждый обычный вопрос имеет **не менее 3** релевантных документов; каждый документ релевантен хотя бы одному вопросу (равномерное покрытие корпуса).
- Вопросы сформулированы **собственными словами**, без копирования фрагментов документов (проверяется тестом: общая подпоследовательность слов вопроса и документа ≤ 7 слов).
- Вопросы-ловушки (`trap`) посвящены темам, которых в корпусе нет (Rust, Kubernetes, Gradle/Android, PostgreSQL EXPLAIN, React). `relevant_docs` пуст, ожидаемый ответ системы — отказ: «В документах нет этой информации». Догадка или выдуманный ответ считаются ошибкой.
- Эталонный ответ (`reference_answer`) — краткий и опирается только на тексты релевантных документов.

### 3.3. Метрики

- **Поиск** (10 обычных вопросов): $Recall@k$ для $k \in \{3, 5, 10\}$ и $MRR$ (глубина 10: если релевантного документа нет в первых 10, $RR = 0$). Ловушки в метрики поиска не входят.
- **Ответы** (все 15 вопросов): Accuracy (доля полностью верных ответов из 10) и Correct Rejection Rate (доля корректных отказов из 5).
- Равные баллы BM25 упорядочиваются по возрастанию `doc_id`.

### 3.4. Запуск в рантайме

Индекс корпуса собирается за секунды без архива дампа: `make index-corpus` (п. 4.9–4.10 `docs/Tech/03-data.md`), затем `benchmark/evaluate.py` считает метрики по `questions.json`.

### 3.5. Проверка набора

`tests/unit/test_benchmark_corpus.py` проверяет структуру (30 документов, 10 + 5 вопросов, ≥ 3 релевантных документа на вопрос, существование меток, покрытие корпуса, отсутствие длинных заимствований, формат ловушек); `tests/integration/test_benchmark_e2e.py` собирает индекс корпуса и проверяет, что для каждого обычного вопроса хотя бы один релевантный документ попадает в первые 10 результатов эталонного BM25.
