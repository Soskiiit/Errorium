# 02-users-and-scenarios.md — Роли пользователей и ключевые сценарии

## 1. Ролевая модель

| Роль | Описание | Основные права и возможности |
| :--- | :--- | :--- |
| **Guest (Неавторизованный)** | Ознакомительный пользователь | Базовый поиск по BM25, просмотр сниппетов, ограничение на RAG (до 3 запросов в сутки). |
| **Developer (Инженер-разработчик)** | Авторизованный пользователь через SSO | Неограниченный BM25-поиск, RAG-генерация решений, сохранение истории запросов, интерактивный граф связанных SO-тредов. |
| **Administrator (Администратор)** | Оператор платформы и системный инженер | Управление пользователями и ролями, мониторинг системных метрик, аудит запросов, запуск переиндексации дампа, управление RAG-моделями и промптами, лимиты API. |
| **External AI Agent (MCP Client)** | Cursor, Claude Code, Windsurf | Программный доступ через Remote MCP Server с использованием личного API-токена пользователя. |

## 2. Сценарии использования (Use Cases)

### Сценарий 1: Интеллектуальный поиск ошибки и получение RAG-решения (Developer)
1. Разработчик вводит аварийный лог, стектрейс или фрагмент кода с описанием проблемы в поисковую строку Web UI.
2. Система токенизирует запрос, извлекает технические токены (`NullPointerException`, `spring-boot`, `PostgreSQL`) и запрашивает Search Engine Core через gRPC.
3. Search Engine Core рассчитывает оценки BM25 по инвертированному индексу и возвращает Top-10 релевантных тредов Stack Overflow.
4. Gateway агрегирует лучший тред и ответы, формирует контекст и отправляет запрос в LLM.
5. Пользователь видит в интерфейсе:
   - Синтезированное готовое объяснение причины и пошаговый рецепт исправления.
   - Список ссылок на оригинальные темы с разбивкой по релевантности.

### Сценарий 2: Интерактивный граф связанных SO-тредов (Developer)
1. Разработчик ищет ошибку и на странице результатов выдачи (`/search`), помимо основного RAG-решения, видит ниже интерактивный граф связанных тредов Stack Overflow.
2. Система отображает узлы (вопросы и лучшие/принятые ответы), где размер узла зависит от Score вопроса, а цвет обозначает тип связи (лучший результат, топ выдачи, дубликаты, треды из ответов).
3. При наведении на узел пользователь видит заголовок, сниппет и статус наличия принятого ответа.
4. Разработчик кликает по узлам графа для изучения дубликатов и связанных обсуждений, перемещаясь между ними без перехода на другие страницы.
5. При необходимости пользователь может перейти на оригинальную публикацию Stack Overflow по прямой ссылке.

### Сценарий 3: Авторизация через SSO (Developer / Administrator)
1. Пользователь нажимает «Войти» на веб-портале.
2. Выбирает провайдера SSO (GitHub OAuth2 / Google OIDC / корпоративный IdP).
3. После подтверждения прав на стороне IdP шлюз Gateway выпускает пару JWT токенов (короткоживущий `access_token` и `refresh_token`).
4. В профиле генерируется персональный Bearer-токен для интеграции с локальным редактором (MCP).

### Сценарий 4: Управление платформой через Admin Dashboard (Administrator)
1. Администратор переходит в защищенную панель `/admin`.
2. Просматривает статус поискового индекса: количество проиндексированных документов $N$, среднюю длину документа $avgdl$, объем на диске.
3. При обновлении дампа запускает задачу потоковой переиндексации через `search_engine_indexer`.
4. Настраивает параметры RAG: системный промпт, температурный режим, используемую LLM (OpenAI, Anthropic, локальная vLLM/Ollama).
5. Просматривает аналитику: популярные запросы, ошибки с нулевой выдачей, распределение времени ответа ядра поиска.

### Сценарий 5: Работа AI-агента через Model Context Protocol (MCP)
1. Разработчик подключает Errorium к IDE Cursor через Remote MCP Server (`https://errorium.ru/sse`).
2. При падении тестов в IDE Cursor вызывает инструмент `errorium_search_solution(query, tags)`.
3. Errorium возвращает в контекст Cursor структурированные факты и код решения.
